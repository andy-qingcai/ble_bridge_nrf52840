# P0 结案报告：幽灵地址事故 + OTA ACK 停摆机制 + 20 轮压测（2026-10-12 晚）

- 平台：nRF52840 DK 形态板 + WCH-Link(SWD) + 参考 SUOTA 设备
- 本晚最终固件：**0.6.3-ackstall**（= E0c 等价基线 + HCI/CONN DBG 日志口(cdc2) + ASSERT 回补 +
  EVT.SCAN adv_type 字段 + 六项 BLE 缓冲扩容 + 地址字节序正名）
- 结论先行：**板卡固件与 SDC 全程无罪**。下午的 connect 全灭是上位机驱动的"幽灵地址"字节序事故；
  P0（OTA ACK 停摆）的真根因在**设备侧 LL 链路短暂失联**，板侧缓冲不足是次生放大器（已扩容修复）。

## 一、幽灵地址事故（connect 全灭的根因）

- 固件 `api_connect` 把 payload 地址字节**原样**放入 Zephyr `bt_addr.val`（小端线序），
  而项目文档写"显示序"且 `parse_scan_payload` 不翻转输出——三层各自"自洽"，合起来是：
  **所有人以为的显示地址 "FF:EE:DD:CC:BB:AA" 实为 val 线序；设备的真实显示序是
  "AA:BB:CC:DD:EE:FF"（= 手机上看到的 MAC）**。
- ackstall 会话的驱动按"显示序"传 "AA:BB:CC:DD:EE:FF" → 固件得到 val={AA,BB,...} →
  目标显示地址 FF:EE:DD:CC:BB:AA **不存在** → initiator 找不到匹配广播 → 5s 静默 →
  cancel 成功回执（status=116=0x74 NOT_READY）。HCI 签名与"引擎死亡"假说完全同型，
  连带把多轮对照实验也拖下水（对照脚本复刻同一错误）。
- **修复 = 契约 v1.4.2 地址字节序正名**：全部含地址字段（CMD.connect / CMD.disconnect
  载荷与成功 body / EVT.SCAN / EVT.CONN）统一**显示序**，固件在边界与 Zephyr val 互转，
  host 直通。端到端验证：扫描直出 `AA:BB:CC:DD:EE:FF`，用它一发连接成功，
  成功 body 回显同序，OTA 满速。

## 二、P0（OTA ACK 停摆）机制：设备侧 LL 短暂失联

HCI 现场两例（E2-T/R12、E2-PB2/R5）一致：

- **断链原因码 = 0x08 Connection Timeout（链路监督超时）**：设备在 OTA 中途停止应答连接
  事件 >4s → 链路死亡。板侧无线电健康（前后扫描正常），host 无任何异常在先。
- 两种表现：失联 <4s → 链路幸存、积压 ACK 迟到（= 今早 P0 原始签名，20 轮压测的 R19
  即此形态：69.7s、块间最大 gap 2.3s）；失联 >4s → 监督超时断链（OTA FAIL）。
- **次生放大器（板侧，已修）**：4KB 块 × 247B MTU ≈ 17 ACL 分片/块 × 流水线窗口 3 ≈
  50 分片在途，而 `BT_CONN_TX_MAX`/`L2CAP_TX_BUF_COUNT=10`——R12 现场抓到
  `bt_conn: Unable to allocate buffer with K_NO_WAIT` → 管道冻结。**六项缓冲扩容
  （CONN_TX 20 / L2CAP_TX 20 / EVT_RX 32 / ACL_RX_EXTRA 16 / SDC_RX 6 / SDC_TX 6）
  后，亚监督超时的抖动可被完全吸收**。

## 三、数据

| 配置 | 结果 | 吞吐 |
| --- | --- | --- |
| 流水线 window=3，缓冲 10（E2-T，修复前） | 9 轮 2 停摆（R4@块47、R12@块151，均 0x08） | 14.2 KB/s |
| 阻塞模式 pipelined=False，缓冲 10（E2-T） | 9/9 零停摆 | 14.3–14.5 KB/s |
| **流水线 window=3，缓冲 ×2（E2-PB2 0.6.2）** | **20 轮 19/20**（R5=0x08 设备失联；R19=2.3s 亚超时被吸收） | 14.2 KB/s |

- 设备侧失联频率（今晚口径）：亚超时短暂失联 ≈1/10 轮；致命长失联 ≈1/20 轮。
- OTA 失败后设备自愈良好（下一轮即可重连），零人工恢复介入。

## 四、结论与去向

1. **板侧工程已到顶**：缓冲扩容 + 既有超时参数下，一切可吸收的抖动已吸收；
   剩余失败全部是设备 LL 静默 >4s，属设备固件域。
2. **设备侧证据包**（交厂商渠道）："OTA 深写流水下设备 LL 静默 >4s → 监督超时 0x08 →
   断链；OTA 重启自愈"——HCI 日志（本地留存）+ 块时间线 + 复现驱动脚本。
3. ** host 侧可选缓解**：`pipelined=False`（阻塞模式）实测零停摆且无吞吐损失，
   对失联敏感的场景可用；默认仍保留流水线（扩容后已稳）。

## 六、吞吐限制定责（2026-10-12 深夜追加）：墙在设备侧，已定量

**问题**：14.5KB/s 的天花板到底在哪一方？四组独立实验与总账：

| 证据 | 数据 | 指向 |
| --- | --- | --- |
| 纯空口需求 | 638,369B @2M PHY ≈ 2,585 包 ≈ 0.7–1.4s | 空口利用率 ~3%，非空口 |
| ping 基线（A+B：USB CDC+固件路径） | p50 = 2.62ms | host 侧可忽略 |
| 块大小缩放 | 2KB×312 块与 4KB×156 块总时长同为 ~44s | 设备侧开销**按字节**计费（flash 写速率），非按块 |
| 连接间隔压到 7.5ms（CMD.conn_update 6,6,0,400） | 43.4s / 14,703 B/s（+1.1%） | 非事件对齐限 |
| 流水线窗口加深（6→8） | window=6 直接 pipeline 超时失败 | 设备吸收不了更深的在途流水 |
| 跨平台对照 | CH592 时代 14.8KB/s ≈ nRF52840 时代 14.2–14.7KB/s | 两个完全独立的 host 平台收敛于同一速率 |

**结论**：墙 = **设备固件的串行写入/处理速率 ≈14.5KB/s（~69µs/字节）**。host、USB、
空口、连接参数、流水线深度均已实验排除。host 侧进一步优化无收益；唯一加速途径是
设备固件改造（flash 写流水/批量提交/ACK 与写重叠），属厂商渠道。
**工具侧已交付的可靠性优化**（缓冲扩容吸收亚秒级抖动、阻塞模式零停摆备选、
0x08 快速判定设备失联）不受此结论影响。
